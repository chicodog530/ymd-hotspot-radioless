# Initial GitHub Repository Setup

This package is prepared to become the root of a `ywd-hotspot` Git repository.

## Recommended first commit from Linux, WSL or the Pi

Using Linux/WSL/the Pi for the first commit is the easiest way to preserve executable bits and LF line endings.

```bash
cd /path/to/ywd-hotspot
git init -b main

chmod +x INSTALL.sh UPDATE.sh UNINSTALL.sh
chmod +x bin/ywd-hotspotctl lab/mmdvm-diag.sh
chmod +x lib/*.py

git add .
git update-index --chmod=+x INSTALL.sh UPDATE.sh UNINSTALL.sh
git update-index --chmod=+x bin/ywd-hotspotctl lab/mmdvm-diag.sh
git update-index --chmod=+x lib/*.py

git status
git commit -m "Initial YWD-Hotspot 0.1.0-alpha5 source"
```

Create the empty repository on GitHub, then add the URL supplied by GitHub:

```bash
git remote add origin https://github.com/OWNER/ywd-hotspot.git
git push -u origin main
```

Replace `OWNER` with the actual account or organization.

## If the first checkout happens on Windows

`.gitattributes` forces the important text/script files to LF in the repository, but executable bits can still be awkward when files are staged from a Windows-only workflow.

After cloning the repository on the Pi, the documented install path explicitly normalizes permissions:

```bash
chmod +x INSTALL.sh UPDATE.sh UNINSTALL.sh bin/ywd-hotspotctl lab/mmdvm-diag.sh lib/*.py
```

That makes the installer robust even if a ZIP upload or Windows filesystem lost Unix execute permissions.

## Do not commit runtime secrets

Runtime configuration is deliberately outside the repository under `/etc/ywd-hotspot` and `/var/lib/ywd-hotspot`. Keep it that way.

Never commit or attach:

- `/etc/ywd-hotspot/config.json` from a real deployment
- `/etc/ywd-hotspot/bm-api.key`
- `/etc/ywd-hotspot/web-auth.json`
- protected backups from `/var/backups/ywd-hotspot`
- private config-history/calibration snapshots
- arbitrary diagnostics before verifying they were generated by the sanitized exporter

The root `.gitignore` contains defensive patterns for accidental local copies of these files.

## Before making the repository public

1. Choose and add a `LICENSE` file.
2. Review `SECURITY.md` and decide how private vulnerability reports should be received.
3. Replace the `OWNER` placeholder in README/docs with the real GitHub owner.
4. Confirm no runtime config, API key, password, backup or diagnostics bundle is staged.
5. Tag only releases that have actually passed the project's test checkpoint.

Alpha5 is currently **under test**, so it should not be described as the known-good release until testing is complete.
